# Session Cartographer 0.6.1

A correctness release for the indexing path. Both fixes address failures that
produced no error and no log line, so neither was visible from the outside: one
dropped events from semantic search under concurrency, the other split the vector
collection across two incompatible key schemes.

## Highlights

- **Hooks index the event they wrote.** Every hook previously appended its event
  and then re-read the log with `tail -1` to index it. With several agent sessions
  appending to one `changelog.jsonl` that is a race — a bounded reproduction had
  only 15 of 60 reads return the writer's own event. Hooks, backfills, and the
  `/wrapup`, `/investigate`, and `/trustmap` skills now pipe the event directly.
- **One point ID, and a wide one.** `index-event.sh` used POSIX `cksum` (32-bit)
  while `embed-events.js` used a djb2 truncated to 31 bits. The two agreed on none
  of 4,000 sampled event IDs, so a collection written by both paths was fragmented
  across two key spaces. Both now use the first 13 hex characters of SHA-256 — 52
  bits, exact as a JavaScript `Number`, identical between the shell and Node.
- **A migration that does not re-embed.** `scripts/migrate-point-ids.js` reads
  vectors back from Qdrant and re-keys in place. It defaults to a dry run and
  reports the scheme breakdown before changing anything.
- **The custom-hook template is fixed**, so the racy pattern stops propagating into
  user-authored hooks.

## Why these were invisible

`index-event.sh` exits 0 both when it indexes an event and when its novelty gate
rejects one as too similar to an existing entry. A lost event and a deliberately
skipped duplicate therefore look identical from outside, which is why a race that
dropped a large share of events under concurrency never surfaced as a symptom.
Point-ID collisions have the same shape: Qdrant upserts, so a collision silently
overwrites an unrelated event rather than failing.

Neither problem announces itself. Both were found by measuring the index against
the logs rather than by anything breaking.

## Upgrading

Install 0.6.1 first, so new events are written under the unified point ID, then
migrate the existing collection:

```bash
node scripts/migrate-point-ids.js            # dry run — reports, changes nothing
node scripts/migrate-point-ids.js --apply
```

The dry run prints how many points sit on each legacy scheme, how many are already
migrated, and whether any two distinct event IDs would collide in the new space. It
leaves points it cannot classify, and points with no `event_id`, untouched.

Order matters: with the writers upgraded first, events created during the migration
land on the new scheme and are skipped as already-migrated rather than orphaned. The
migration is idempotent and safe to re-run; a second pass on a migrated collection
reports `would move 0`.

If you skip the migration nothing breaks — existing points stay searchable by vector
— but points on the old schemes are unreachable by ID lookup and will not be updated
in place when their event is re-indexed.
